# IPHS 400 MP2 Report — Adam Leider

## What I built and the decisions I made

For this project, I built a Content Management System (CMS) using Claude Code for the Center for Global Engagement (CGE) at Kenyon College. The basic idea is for the CGE to appoint students studying abroad as ambassadors, who can post about their experiences on specific programs for other students at Kenyon and potentially other universities to be able to look at when considering their own study abroad journey. 

The site features a home page with links to continent sub-pages, which in turn have links to country sub-pages, which have links to program pages on which the specific posts are settled. Ambassadors create drafts and push them (somewhat similar to the github system), and CGE staff (admins) can fully publish students' posts. The ambassador editing page features a guide for how to write markdown files, including how to put photos into their posts. The admin pages include pages with different site metrics and overviews, as well as a pending queue where they can view, bounce back to draft, or publish ambassador pushed posts. The site is aesthetic and well-designed, and includes standard site features such as a footer with "about" and "contact us" pages and organizational features like a visible breadcrumbs trail for people navigating the site. 

I chose this project because I deeply wished a service like this was available to me when I was looking at study abroad program options. I had to sort through reviews on different sites online, many of which were disorganized, poorly managed, or hard to sort through, and also which often didn't feature many reviews from programs I was interested in. This would allow for a Kenyon-specific site that the CGE could manage to display different aspects of experiences at a myriad of study-abroad programs, all of which would exist through a Kenyon-specified lens. 

Working with Claude Code was a fun and educational experience. While I generally made design decisions and managed the project, and Claude built the project based on my instructions and handled lower-level implementation decisions, both Claude and I sometimes made important contributions to each other's domains. For example, when Claude wanted editable slugs for posts, I decided against it, favoring keeping links stable after drafts are published to maintain ease of site navigation and avoiding confusion with ambassadors not knowing what a slug is. I also thought it would be important that when staff accounts get deactivated, their work is saved. While Claude wanted a plain dashboard layout for the staff page, I opted for a WordPress style homescreen with a preview of the actual site and a sidebar of important tabs (metrics, pending queue, etc.).

Aside from what I edited of Claude's decisions, I also added a number of features to the created project of my own - a pending "submit for review" status, a Continent→Country→Program page tree with demo data, topics on posts with a filter, footer pages, a navigation bar with breadcrumbs, and ambassador drafts being deleted when deactivated (but not staff ones). I also added a number of stretch features later - post tags, a search function, media uploads (pictures on posts), and a formatting help box for students (and potentially staff) who don't know markdown.

There were multiple other features that I had to cut from the scope, either because I didn't find them necessary or they would've been too hard to implement. These included a trash that saved posts with a custom auto-delete function, scheduled publishing for posts, suggested edits, and messaging/comments for visitors on the site (which would require a live server). 

## Where Claude drifted

Claude did drift a bit as well, and through my own observation as well as using Claude's web chat to assist with understanding, I was able to catch it when it did. For example, Claude named all posts "dispatches" on the site, which I found confusing and unnecessary, and never asked for. Claude also added some rules I never discussed into the spec, like adding "-2" or "-3" to the end of duplicate slugs, staff not being able to directly publish someone else's draft, and staff drafts getting deleted with account deactivation like ambassadors. None of these were specified, and these were largely caught by me reviewing specs with the Claude chat interface. Code review also caught some drift, like when the screens showed internal code names "Admin" and "Editor" instead of the names I instructed it to, "Staff" and "Ambassador." Not everything was caught the same way: the admin pages were unstyled for the entire build (#13) while every test and review passed, and only taking the required screenshots revealed it. Testing the site myself as an Ambassador caught something else entirely: the raw Markdown editor would confuse students, which led to the formatting help box.

## Skills and workflow

Matt Pocock's workflow was easy to follow and quite enjoyable for me to use. The workflow is intuitive and optimized - grilling me (/grill-with-docs) to fully fill in details for the specs (/to-spec), which are then turned into manageable tickets (/to-tickets), which are then implemented test-first (/implement, /tdd) and reviewed (by a separate agent, /code-review) in Claude Code. For TDD, I asked for a separate services layer so the core rules (slug generation, status transitions, and deactivation) would be tested directly, not only through the website. I also used skills like /wait-what to explain things for myself and /ask-matt when lost. /code-review was invaluable, as it caught a number of bugs, such as the cascade-delete bug and the race condition, but also did cause problems like when the background run hung and Claude reviewed its own code. For my own workflow, I used the Claude chat interface to help manage and organize the project, and to contextualize myself after breaks from it. It also helped me to understand and work with the Claude Code interface. As problems came up, I wrote rules into CLAUDE.md, such as always running reviews in the foreground, pushing after every ticket, and using relative links, so the same mistake wouldn't happen twice.

## Budget: plan vs. actual

In terms of my original speculation for the budget, I had guessed about 30% per ticket, which turned out to be a pretty large overestimation. Core tickets cost me about 10%, but I did do a design pass with Opus, which used about 94% of a 5-hour usage window, more than all 8 core tickets combined. I assume this is because of the image-processing work it had to do, and the usage of Opus on high effort. My extra features cost more than the core tickets, and I do wonder if this has something to do with them being iterated over multiple times as I edited and made suggestions to my liking. I did use Sonnet instead of Opus for the grill (accidentally forgetting to switch the model after my computer restarted), which fortunately ended up working great without any major issues. Some of the budget data is mislabeled: 16 turns are unlabelled because I didn't always set the phase before working, and a stray T09 row from a later session inflates search's cost. The tracking is only as accurate as the labels, so next time I'd set the phase at the start of every session.

## What I'd add next

As for the future of this project, there are a number of features I would love to implement. The first would be adding live-server infrastructure, so I could really run and test the site, and add features for site visitors such as account creation and management, comments on posts, and direct messaging with each other, staff, or ambassadors. I would add some of the stretch features that got cut as well, like a trash with an auto-delete after a certain period of time (that could be customizable), a scheduled publishing feature, and suggested edits on posts/drafts. 

## Takeaway

My biggest takeaway from this project is how to manage working with Claude Code on an enterprise of this scale. It's important to break work into chunks, have many human-approval gates, make sure each section of the work is understandable and being reviewed, and most importantly, to establish a consistent plan base to work from so that the project itself is geared towards one's intentions. The creative aspects and unique elements of the project will ultimately come from the emphasis on those aspects of the workflow and project management.
